# 第十章 分布式协作服务ZooKeeper

## 1 ZooKeeper概述

ZooKeeper本质上是一个分布式的小文件存储系统，通过提供类似于文件系统目录树的数据存储功能，对目录树中的数据节点进行有效管理，从而维护和监控存储数据的状态变化

### 特性

- 顺序性
- 原子性
- 一致性
- 可靠性
- 实时性

### 集群角色

- 客户端节点`Client`
- 服务器节点`Server`
	- 领导者`Leader`：ZooKeeper集群工作的核心，事务请求（如写操作）的唯一调度和处理者，保证集群事务处理的顺序性
	- 跟随者`Follower`：处理客户端非事务（如读操作）请求，转发事务请求给领导者服务器，参与事务请求提案投票和领导者选举投票
	- 观察者`Observer`：处理客户端非事务请求，转发事务请求给领导者服务器

### 数据节点`Znode`

谈及分布式时，通常说的“节点”是组成集群的每一台物理机器，即机器节点

在ZooKeeper中，还存在另一类“节点”，是指数据模型中的数据单元，称之为数据节点——Znode

### 会话`Sessions`

指客户端与服务器之间进行的一系列交互过程

会话的生命周期涵盖了客户端与服务器建立连接的整个过程

### 事件监听器`Watcher`

ZooKeeper中的一种事件通知机制，用于监视ZooKeeper中数据节点的变化

具有一次性和轻量级两个特点：

- 一次性：一个Watcher只能触发一次，一旦Watcher被触发，ZooKeeper就会将其删除
- 轻量级：Watcher的事件通知非常简单，它只包含通知状态、事件类型和节点路径三部分内容

## 2 Znode

### Znode特点

Znode兼具文件和目录两种特点，每个Znode由三个部分组成

- stat：指状态信息，描述该Znode版本、权限等信息
- data：指与该Znode关联的数据
- children：指该Znode下的子节点

ZooKeeper的服务器和客户端都会严格检查Znode的数据大小，并将其限制在1M以内，但常规使用中都会远小于此值

### Znode节点类型

- 持久节点：节点被创建后就会一直存在于ZooKeeper服务器上，直到有删除操作主动清除这个节点，适用于需要长时间保存数据的场景
- 临时节点：生命周期与客户端会话绑定在一起，如果客户端会话失效，节点就会被自动清理掉。临时节点智能作为叶子节点
- 顺序节点：可确保节点创建的顺序性和唯一性，可以是持久的也可以是临时的，常用于实现分布式锁和分布式队列等

## 3 ZAB协议

ZAB协议是ZooKeeper的核心

### 工作过程概述

崩溃恢复（选举，发现，同步）+消息广播（广播）

当整个服务框架在启动过程中，或是当领导者服务器出现网络中断、崩溃退出与重启等异常情况时，ZAB协议就会进入崩溃恢复模式并选举产生新的领导者服务器，当集群中有过半的机器与新的领导者服务器完成了数据同步之后，服务框架就会退出崩溃恢复模式，进入消息广播模式

### 崩溃恢复

为避免数据不一致的隐患，ZAB协议选举算法必须确保那些已经在领导者服务器上提交的事务最终被所有服务器都提交，同时丢弃那些旨在领导者服务器上被提交的事务

### 消息广播

针对客户端的事务请求，领导者服务器会生成对应的事务提案，并将其发送给集群中的其他服务器，然后收集各自的选票，最后进行事务提交。当收到超过半数跟随者服务器反馈的确认消息之后，就可以开始事务提交

## 4 ZooKeeper命令

- 创建Znode

	`creat [flag] path data`

- 获取数据

	`get path [watcher]`

- 更新数据

	`set path data [version]`

- 列出子项

	`ls path [watcher]`

- 检查状态

	`stat path [watch]`

- 删除Znode

	`delete path [version]`
